# 17. Break report

Findings from trying to break Project Atlas locally (in-process apps, a private Postgres, no live
systems). Newest cycle last. Severity follows the scale used for the exercise: Critical (cross-tenant
access, privilege escalation, secret exposure), High (data loss, business rule bypass), Medium (500s or
hangs on hostile input, silent fail-open settings), Low (hardening gaps), Info (things that held).
Work list: `NEXT.md`.

| # | Sev | Area | Finding | State |
|---|-----|------|---------|-------|
| 1 | Medium | Config | `RATE_LIMIT_WINDOW` was an unchecked string. `abc`, `1 parsec`, an empty value or `0` booted fine and then every business request answered 500 (the limiter threw per request). A negative value (`-5 minutes`) and a bare number (`60`, read as 60 ms) booted fine and limited nothing. The same held for `PRIVACY_RATE_LIMIT_WINDOW`. | Fixed: both are validated at boot (`rateLimitWindowSchema`, one second to seven days, `<number> <unit>` only). Tests in `packages/config/test`. |
| 2 | Info | Rate limit | The limiter's in-memory store is a 5,000-entry LRU, so many unique clients cannot grow memory without bound. | Held. |
| 3 | Low | Rate limit | Clients are told apart by `request.ip` with `trustProxy: true`. That is the first `X-Forwarded-For` entry, which a client chooses unless the edge overwrites the header. Vercel does overwrite it, so the launch deployment is not affected; behind a proxy that only appends, one client could pick fresh buckets at will, or push others' buckets out of the LRU. | Accepted for launch, documented in `registerRateLimitedRoutes`. Revisit if the API ever moves behind another proxy. |
| 4 | Medium | Config | `CORS_ORIGINS` entries were not checked. `https://app.example.com/` (trailing slash), `app.example.com` (no scheme), a URL with a path, or `null` started the service fine and then matched no browser `Origin`, so every browser call failed with a CORS error and nothing in the logs said why. | Fixed: a trailing slash and upper-case are forgiven (normalized to the exact origin form), and an entry that can never match stops the boot with the entry named. Tests in `packages/config/test/cors-origins.test.ts`. |
| 5 | Low | Config | `CORS_ORIGINS=*` is accepted in production although `docs/16` says never to use it and the config comment says development only. The API authenticates with bearer tokens, not cookies, so a wildcard does not expose a session, but the rule is not enforced. | Open: needs an owner decision, because the live preview may rely on `*` (see `NEXT.md`, "Needs Nikshey"). |
| 6 | Medium | Auth | When the Supabase key set (JWKS) could not be fetched or read (project paused, network failure, 5xx, a page that is not a key set), token verification answered **401 on every request**. The web app treats a 401 as "this session is dead" and signs the user out, so a short outage or a paused project logged everyone out instead of showing "try again". | Fixed: key-set failures now answer 503 `UPSTREAM_UNAVAILABLE`; a bad token on a healthy key set is still 401. Tests in `packages/auth-kit/test/tokens-attacks.test.ts`. |
| 7 | Low | Auth | `jwtVerify` was called without required claims, and jose treats a missing `exp` as a token that never expires. Exploiting it needs a validly signed token, which Supabase never issues without `exp`, so this is hardening. | Fixed: `exp` and `sub` are required. |
| 8 | Medium | Jobs ingestion | A job board that put a NUL byte (`\u0000`) in any title, location or description made Postgres refuse that posting, so it was counted as rejected. Any rejected posting makes the run skip the sweep that deactivates closed roles, so one such posting kept every stale posting of that board active and recommended for as long as the board listed it. The same fields also stored other control characters (BEL, ESC) and bidirectional overrides (U+202E), which garble logs and can make a title read as something else. | Fixed: every posting text field is stripped of NUL, control characters (except tab, line feed, carriage return) and bidi overrides/isolates before it is stored (`stripUnsafeChars` in `job-sources/common.ts`). Tests: `services/jobs/test/hostile-postings.test.ts` (fails without the fix), `job-source-mappers.test.ts`. |
| 9 | High | Profile / ai | `parseResumeText` used an email pattern with open-ended quantifiers (`[a-zA-Z0-9._%+-]+@...`). On a run of local-part characters with no `@` (a resume that is one long word, or `aaaa...`, `----...`, `1111...`, `2020-2020-...`) it rescanned from every start position: quadratic time. A 200,000-character `text/plain` upload (the extraction cap) kept the function busy for minutes, far past the 30 s limit, and the parse runs inside the upload request. One authenticated request could pin an instance; 20 uploads a minute per address could pin many. It also affected `POST /v1/resumes/:id/optimize` and anything else that parses resume text. Found when the first sweep hung the test run for over six minutes. | Fixed: the local part, domain and top-level domain are bounded (64, 255, 24). The parse of any 200,000-character shape in the sweep now takes under 100 ms. New `packages/ai/test/adversarial-input.test.ts` checks growth on 37 hostile shapes at two sizes (it fails in under two minutes against the old pattern instead of hanging). |
| 10 | Medium | Profile | A PDF could carry a decompression bomb: a page content stream of Flate data that inflates about 1,000 to 1. A 299 KB PDF made pdf.js spend 3.1 s and about 670 MB; the upload limit (1 MB by default) allows roughly 1 GB inflated, past a function's memory, and it runs inside the upload request. The DOCX path already had a zip-bomb guard; the PDF path had none. | Fixed: before pdf.js sees the file, every zlib-looking stream is inflated with a cap (32 MB each, 128 MB together; `assertSafePdfStreams`), so a bomb is refused with 413 "too large or complex". A 300 MB bomb is now refused in 26 ms and a 1 GB one in 152 ms. Tests in `services/profile/test/extract-text.test.ts`. |
| 11 | High | Applications | Status moves were read, validated, then written with an unconditional `UPDATE ... WHERE application_id = ...`. Two requests that both read the same status both passed validation and both wrote. Observed: 20 simultaneous `queued` requests all answered 200 and left 20 events; 15 simultaneous `submitted` requests published `application.submitted` 15 times; and with `offer` and `rejected` sent together an application was recorded as `interviewing -> offer` after it had already been `rejected` (a terminal status), so the head and the trail disagreed with the lifecycle. Reachable by a double click, or the owner and staff acting together. | Fixed: the update only applies while the application is still in the status the move was validated against (`AND status = from_status`); the loser gets 409 `CONFLICT` and nothing is written or published. Tests: `services/applications/test/applications-races.test.ts` (failed 3 of 5 before, passes repeatedly after). |
| 12 | Low | Applications | Thirty identical creates at once (same idempotency key, same body) answered 201 once, 200 for most, and **409 for 12 of them**, because the winner's row was invisible to the key lookup but visible to the "already applied to this job" check. A retry racing its original saw an error for something that had succeeded. | Fixed: a row with the same key and the same request found at that point is a replay (200). |
| 13 | Medium | All list endpoints | The page `cursor` is opaque, but any string is accepted. Valid JSON that was not a cursor this API issued went straight to the database as a timestamp or a uuid: `{"createdAt":"not-a-date","id":"..."}` (and `2026-02-31`, which `Date.parse` accepts but Postgres refuses) answered **500** on applications, jobs, recommendations, resumes, messages and a company's contacts; other malformed shapes (numbers, objects, a missing id) were silently treated as the first page. Only the admin roster validated its cursor. | Fixed: one pair of validators in `@atlas/utils` (`parseTimeCursor`, `parseScoreCursor`: real calendar date and clock time, uuid ids, finite bounded scores) is used by every list query, including the roster; a cursor that is not exactly what the API issues is a 400 `VALIDATION_ERROR` "Invalid cursor". Tests: `packages/utils/test/cursors.test.ts` (42 cases) and six forged-cursor cases over HTTP in `applications-flow.test.ts` (all failed before). |
| 14 | High | Config / auth | `SUPABASE_URL` was any URL. With the trailing slash the dashboard shows (`https://abc.supabase.co/`) the expected issuer became `https://abc.supabase.co//auth/v1`, which no token carries: the service started, then refused **every** request as unauthenticated, and the web app signed everyone out. `http://` (a key set fetched in the clear), credentials in the URL and non-web schemes were accepted too. | Fixed: the value is reduced to its origin (a trailing slash or path is forgiven) and anything that is not `https` (or `http` on localhost for a local stack) stops the boot. Tests: `packages/config/test/supabase-url.test.ts`. |
| 15 | Medium | Config | `MESSAGING_DRIVER=memory` is what `.env.example` shows for local work. Pasted into Vercel's settings it would drop every cross-service event without a sound (each function is its own process), which is the failure the serverless default exists to prevent; the default only covered the variable being unset. | Fixed: on Vercel `memory` (or an empty value) is not honoured and the outbox is used. Tests in `packages/utils/test/vercel.test.ts`. |
| 16 | Low | Config | `CRON_SECRET` kept surrounding whitespace (a secret pasted into a dashboard often keeps its newline), so the comparison could never succeed and the scheduler got 401 for ever; one with whitespace inside could never match a header value. | Fixed: surrounding whitespace is dropped, whitespace inside stops the boot (`cronSecretSchema`, used by the five services that take it). |
| 17 | Low | Docs | `.env.example` left out variables services read (`BODY_LIMIT_BYTES`, `DATABASE_POOL_MAX`, `MESSAGING_*`, `LOG_PRETTY`, `HOST`). | Fixed, and `packages/utils/test/env-example.test.ts` fails when a service reads a variable the file does not document. `REDIS_URL` and `SUPABASE_ACCESS_TOKEN` remain in the file although no service reads them (Redis is not used). |
| 18 | Low | Web app | `apps/web` sent no security headers at all (the admin console already did): the dashboard, which holds resumes and an account-deletion button, could be framed from another site (clickjacking), content-type sniffing was on, the full address (job and application ids) went to other sites in the Referer, and `X-Powered-By: Next.js` was sent. | Fixed: `X-Frame-Options: DENY` plus `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` that switches off camera, microphone, location, payment and USB, and no `X-Powered-By`; the admin console got the same additions. Checked on a running build (pages carry the headers, the fingerprinted bundles keep `immutable`). Tests in `apps/*/test/security-headers.test.ts`. A full Content-Security-Policy is not set: Next's inline bootstrap scripts need a nonce setup, which is its own piece of work. |
| 19 | **High (launch blocker)** | Profile bundle | **Every PDF resume failed to parse in the deployed bundle.** pdf.js runs its parser as a separate worker module that it loads by file name next to the code that asks for it; inside `api/profile/index.js` that is `api/profile/pdf.worker.mjs`, which does not exist (the bundler cannot inline a file loaded by name, and `vercel.json` includes only the canvas addon). Every PDF upload ended as `status: failed` with "We could not read this file", the most common resume format. Text and DOCX worked, and every test passed, because the tests run the TypeScript sources, where the worker is found inside `node_modules`. Found by the first end-to-end run of the committed bundles (`Setting up fake worker failed: Cannot find module .../api/profile/pdf.worker.mjs`). | Fixed: the worker is passed to pdf.js as the data URL that `pdf-parse` ships (`PDFParse.setWorker(getData())` from `pdf-parse/worker`), which needs no file. Profile bundle is now 9.2 MB (was 5.5). New test `packages/auth-kit/test/bundles-e2e.test.ts` boots all ten committed bundles over real HTTP against Postgres and a stand-in key server and uploads a text, a PDF and a DOCX resume through the profile bundle (failed before the fix). |
| 20 | Low | Logging | The logger redacted only a handful of exact paths (`req.headers.authorization`, `password`, `*.access_token`, ...). The same secrets one level over (`headers.authorization`, `request.headers["x-api-key"]`, `*.secret`, `*.token`) and a resume's `parsed_text` would have been logged in full. `redact()`, `maskEmail()` and `maskToken()` in `@atlas/utils` are used nowhere, although their header comment said the shared logger applied them. | Fixed: the redaction paths cover those shapes (tests in `packages/utils/test/logger.test.ts`), the logger takes an optional `destination` so tests can read what it wrote, and the helper's comment now says what it is. |
| 21 | Medium | Profile | The uploaded file's name was stored as the client sent it. A NUL byte or a name over 400 characters made the insert fail, so the upload answered **500 after the file had already been written to storage** (an orphaned blob each time); an empty name was stored as an empty string, breaking the API's own `min(1)` contract; control characters and a right-to-left override (`resume\u202Egnp.txt` shows as `resumept.png`-style reversed text) were stored and shown back. ## What was checked and held

- `vercel.json`: every `/v1/...` and `/internal/<service>/...` route that each deployed service declares resolves to that service's function, every rewrite destination has a bundle and a function entry, and the service-local `/internal/drain`, `/health` and `/metrics` are not routed at all. New test `packages/utils/test/vercel-routing.test.ts` (it fails when a rewrite is removed).
- Drain and ingest secret checks (`isAuthorizedDrainRequest`): hashed and compared in constant time, no length oracle, empty secret never matches, a duplicate `Authorization` header (joined with a comma by Node) is refused, a secret containing spaces fails closed.
- Token forgery (new `tokens-attacks.test.ts`, all refused with 401): `alg: none` (with, without and with a junk signature), HS256 signed with the public key as secret (PEM, JWK JSON and raw coordinates), a token signed by another key under the right, an unknown or no `kid`, an embedded `jwk` header, `jku` and `x5u` pointing at an attacker, a payload swapped under a valid signature, wrong issuer (including a trailing slash), wrong or missing audience (string and array), `nbf` in the future, junk and 1 MB tokens, a missing or non-uuid `sub`, an unknown role, a non-uuid organization, and role or organization supplied through `user_metadata` or the top level of the token (ignored).
- Ownership checks read: resumes, messages, applications (owner or same-organization admin/owner, 404 otherwise), recommendations (own, or a member of the caller's organization), contacts (a company's contacts only to someone who applied there), learning metrics and job ingest/sources (platform admins only). All answer 404 for what the caller may not see.
- Job-board reading: the request URL is the provider's fixed origin plus a token checked against a pattern (and checked again after the URL is built); redirects are refused; the response is capped at 25 MB by header and by streamed size; the deadline holds even for a `fetch` that ignores the abort signal; error text stored on the source is fixed, never copied from the response. Hostile postings ingested end to end against Postgres: `javascript:` and `data:` apply links are stored as no link, markup in a title is kept as text, a 100 KB title and a 500 KB description are cut to 300 and 200,000 characters, entries with no id or the wrong shape are skipped without failing the board.
- The other parsing regexes in `packages/ai` (phone, URL, month/year, date ranges, section headers, bullet and keyword matching) and `extractSkillKeywords`/`analyzeResumeForJob` grow linearly on the same 37 shapes, including a keyword that is itself a pattern (`(a+)+$`), which is escaped and matched as text.
- Uploads: the DOCX guard already refused lying headers, too many entries, encrypted entries, unknown compression, truncated and offset-rebased archives, and hidden extra directory records (existing tests); text uploads reject NUL, control-character soup and known binary signatures; the declared content type is checked against the bytes and never echoed.
- Thirty creates for one job with different idempotency keys: one 201, twenty-nine 409, one row, no 500 (the unique indexes hold). Outreach's send and mark-sent already claim a message with a conditional update; scheduling is switched off with delivery. `setScheduled` is an unconditional update, which would race a send if delivery were ever enabled (noted in `NEXT.md`).
- Six simultaneous deletions of one account (new test in `delete-account.test.ts`, run repeatedly): all answer 200, one tombstone, no leftover rows, no deadlock.
- Request bodies, content types, query strings and path ids on the applications service (new `body-fuzz.test.ts`, 76 cases): empty, truncated, BOM-prefixed, null/array/scalar bodies, prototype keys, duplicate keys, NUL and lone surrogates, huge numbers, 5,000-deep nesting, wrong content types, a body over the limit (413), unsupported methods (404), malformed and path-traversal ids, odd `limit`/`cursor`/filter values. Every one is a 4xx in the standard envelope with a request id and no stack or driver text.
- Frontends, by reading and by existing tests: no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or `document.write` anywhere in `apps/`; the one external link built from API data (the employer's apply page) goes through `safeExternalUrl` (http/https only) with `rel="noopener noreferrer"`; the `mailto:` builder percent-encodes every field, strips line breaks from the subject and accepts one plain recipient; the sign-in redirect (`next`) accepts only one-slash same-origin paths and rejects backslashes, control characters (a tab turns `/<TAB>/evil.com` into `//evil.com`) and encoded forms; the roster CSV export and import are formula-injection safe (existing tests). Not done: driving the pages in a browser with hostile data (no Playwright run this stretch).
- The committed bundles, booted for real (the new `bundles-e2e.test.ts`, 19 cases): all ten start with Vercel's environment, answer `/health`, turn an anonymous caller and a forged token away with 401 in the standard envelope; auth `me` and export work; only a platform admin can ingest jobs, and the posting is then listed with its employer; the scheduler route needs the secret; resumes can be uploaded and optimized; applications can be created, replayed and moved to `submitted`; a PDF decompression bomb is recorded as "too large or complex" in well under five seconds; another user gets 404 for a resume and an empty application list. The bundles are byte-for-byte repeatable (two builds, identical hashes), the only package left external is `@napi-rs/canvas` (installed for the function by `vercel.json`), and no bundle contains a private key or an access key (the one match for `service_role` is a comment).
- Secrets: no JWT, `sb_secret_`, private key, AWS/GitHub/Slack/OpenAI-style token or `postgres://user:password@host` URL with a real host in any added line of any of the 181 commits on any ref; `.gitignore` covers `.env*` (except the example), `.atlas-storage`, `.atlas-secrets`, logs and build output; none of the ten bundles contains a key. Logs: `x-request-id` is never trusted (every request id is a fresh uuid), a user-supplied line break or ANSI escape stays inside one JSON line, and a database error carries the failing value only in its `message` (Postgres itself masks the bound parameters as `'...'`).
- Roster CSV import (`services/admin/test/csv-hostile.test.ts`, 15 shapes at two sizes): commas, newlines, bare carriage returns, an unclosed quote, quotes inside fields, doubled quotes, one enormous cell, many tiny rows, many columns, NUL, formula prefixes. Parsing grows linearly and every failure is a clean 400 or 413. The remaining regular expressions in the services (referral relevance, header normalization, timestamps, uuids) are simple and bounded.
- `RATE_LIMIT_MAX` of 0 is refused at boot (`min(1)`).
- `/health`, `/metrics` and `/internal/*` are exempt because they are registered outside the limited scope, not by path matching, so no path trick can move a business route into the exempt set.
